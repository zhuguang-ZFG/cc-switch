## 关键机制实证（本轮新确认）

1. **NewAPI priority：数值大者优先**（此前靠 hubway 注释推断，本轮实证）。
   证据：`deepseek-v4-flash` 同时启用在 ch15（p50）与 ch149（p-20），
   历史 1462 vs 183 命中——高值主导；因此备份腿必须取**更低数值**，-30 合规。
2. **渠道列表 API 静默截断 `page_size`**：`page_size=200`（与 500）都只回
   **100 条**（实测 `items=100 total=103`，id 覆盖 2..178）。**ch179 不在其中**。
   首次 --apply 因此报 `not visible after POST`——已修：onboarding 脚本改分页
   全量取（`fetch_channels` 逐页直到 collected>=total，不足即 raise）。
   遗留影响见「风险与备忘 #3」。
3. **status 端点契约**：启停必须 `POST /api/channel/{id}/status {"status":N}`；
   对 `/api/channel/` 的 **PUT 带 status 字段会被拒**（HTTP 200 + `Invalid
   parameters`，success=false）——首次启用即卡在此，已改为 status 端点 + 读回校验。
4. **建渠顺序 = 禁用态先取上游证据**：`/api/channel/test/{id}` 对 status=2
   渠道照常实测上游（不依赖启用态），因此"上游证明"与"启用"可解耦——
   本脚本据此把 enable 放在 channel test 通过之后，任何启用后断言失败即回滚禁用。
5. **冒烟失败集可归因**：本轮 FAILURES 与 **19:25 基线逐字相同**
   （`channel model isolation` / `fallback channel posture` / `primary opus
   pool posture` / `pool capacity claude-opus-5`）——第 4 项在 19:25（本轮变更
   之前）已出现，非本轮引入；本轮 **零新增 FAIL**。

   改 `POST /api/channel/{id}/status`。

   显示为间歇窗（后续健康窗 13/14）。因此两处门禁改**时间展开重试**

   抢流量只会把可用性从"桥健康=100%"降到"最差 30%"。备份档 + auto_ban=1 才是
   正确 fail-closed 姿态。

## 风险与备忘

1. **上游间歇性**：健康窗 13/14、故障窗 0/5。5xx 属 NewAPI
   `AutomaticRetryStatusCodes`（含 503），生产路径会重试到其它腿；且 503/429
   不在 `AutomaticDisableStatusCodes`（401,402,403,502）内，故不会误触
   auto_ban 连锁。作关键链路不可依赖，仅备份。
2. **桥依赖**：ch149 是本机桥（8791）；桥挂时 `glm-5.3-flash` 现在有直连兜底
   （本渠道），这是本次接入的主要收益。
3. **门禁盲区（存量缺陷，非本轮引入，未改）**：`newapi-local-smoke.py`
   （:1174）与 `guardian.py`（:823）都用 `page_size=200` 单请求取渠道表，
   被服务端截断到 100 条 → **ch179 及 id>178 的渠道对"channels 总数/意外禁用
   归因/渠道模型隔离"检查不可见**（实测 ch179 in inventory = False）。
   本轮 ch179 的验证因此完全依赖直接读库 + 分页读 API + 渠道自测 + drill。
   修法=两处分页（与 onboarding 脚本同款），因涉政策门禁改动需评审后单独落。
4. **凭据**：key 经聊天明文传递（同前例）；本轮全程仅 env 传递，未写入
   DB 以外的文件、未回显（DB 内渠道 key 属必要存储）。
5. **套壳身份未明**：响应注入约 1.6k 前缀 token（缓存命中），计费按本地
   ModelRatio（0.075/3.333 存量）走网关默认。
